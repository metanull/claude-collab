# Wake-on-LAN on the Ubuntu machine: what worked and why

Findings from setting up and testing wake by magic packet between a Windows PC and an Ubuntu desktop joined by a
direct network cable. No machine-specific value is recorded here; `IFACE` is the Ubuntu machine's wired interface and
`PROFILE` its NetworkManager profile. `ubuntu/setup/setup-wol.sh` applies the method, `ubuntu/setup/verify.sh` checks it.

## The setting belongs on the NetworkManager profile

```bash
sudo nmcli connection modify PROFILE 802-3-ethernet.wake-on-lan magic
sudo nmcli connection up PROFILE
```

Two other ways were tried first and did not last:

- **A NetworkManager `conf.d` default** (`ethernet.wake-on-lan=64` matched on the interface) never applied. On Ubuntu
  the wired profile is generated by netplan and carries its own explicit wake-on-lan value, and a profile's own value
  wins over a global default.
- **A one-off `ethtool -s IFACE wol g`** arms the adapter until NetworkManager next activates the device, which
  includes every resume from suspend. Observed: the first magic packet woke the machine, after that the adapter
  reported `Wake-on: d` and the second packet did nothing.

With the value on the profile, the adapter stayed armed across suspend/resume cycles and across a power-off and cold
boot.

## How to tell it is armed

| Check | Needs root | Expected |
|---|---|---|
| `nmcli -g 802-3-ethernet.wake-on-lan connection show PROFILE` | no | `magic` |
| `cat /sys/class/net/IFACE/device/power/wakeup` | no | `enabled` |
| `ethtool IFACE` | yes | `Supports Wake-on:` contains `g`, and `Wake-on: g` |

If `Wake-on` is `d` or device wakeup is `disabled`, the machine cannot be woken over the network and needs its power
button.

## What was tested

Magic packet sent as a UDP broadcast (ports 9 and 7) from the Windows PC's wired adapter, Intel wired adapter on the
Ubuntu side.

- **Suspend to RAM (S3, `deep`)**: wakes; answers ping roughly 10 seconds after the packet. Repeated several times,
  the adapter still armed after each resume.
- **Power-off (S5)**: wakes; the machine boots and answers ping about a minute after the packet, and SSH is reachable
  shortly after with nobody logged in at the desktop.
- **Restart**: the profile value and the armed state are still there after a cold boot.

Not tested: hibernation, a wake through a switch or router, other adapters, firmware settings other than the ones the
test machine had.

## Things that can still stop it

- **The packet must arrive on the armed port.** It has to leave the sending machine through the adapter that shares
  the cable or segment with `IFACE`. A packet sent over another network (for example Wi-Fi) never reaches the wired
  card. On a machine with several adapters, bind the sending socket to the right one.
- **Firmware.** Settings such as "Wake on LAN", "ErP" or "Deep sleep" in the BIOS/UEFI can cut power to the port when
  the machine is off. A sign that the port is still powered: the other end of the cable keeps a link (typically at a
  reduced speed) while the machine sleeps or is off; "disconnected" there means the port is unpowered.
- **A slow suspend is not a failed suspend.** On the test machine a suspend requested shortly after a resume was
  sometimes delayed by a minute (`systemd-sleep: Failed to freeze unit 'user.slice'`) and then completed normally. Wait
  before concluding that the machine did not suspend. Cause not investigated; unrelated to Wake-on-LAN.
- **Link-local addresses on a direct cable.** With no DHCP server on the cable both ends get link-local addresses.
  That is enough for the magic packet and for ping; in our setup SSH was used over the home network instead.

## Undo

`sudo bash ubuntu/setup/setup-wol.sh --undo` puts back the value the profile had before the script changed it.
